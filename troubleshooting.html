Troubleshooting

Type what you see, or paste an error message, to find the fix.

Quick fixes

One line per problem. If a fix doesn't hold, check misleading errors below.

Errors that point the wrong way

Each message here points to the wrong cause. Open one to see the real one.

[TxRxResult] There is no status packet!Whole bus dead, yet each motor works on its own
Real cause

Two motors share an ID. They answer at the same time and garble every message on the bus. It looks like a power or cable fault.

Fix

Scan each motor on its own and fix the duplicates. See Motor Configuration.

device descriptor read/64, error -110 or unable to enumerate USB deviceAdapter plugged in, but no bus appears
Real cause

A USB connection problem. The adapter has power but the Jetson never sees it.

Fix

Try a new cable first, then plug straight into the Jetson with no hub, then try another port.

torch.cuda.is_available() returns FalsePyTorch installed, GPU not used
Real cause

The wrong PyTorch build, or the wrong environment. Either the CPU build was installed (look for +cpu in the version) or torch went into conda.

Fix

Reinstall from the Jetson index into a venv on system Python 3.10. See Software step 4.

Motors answer every scan but never moveLoad stuck at 1024 + Torque_Limit, current 0
Real cause

The motors have enough power to talk, but not to move. A lit LED doesn't prove otherwise: it is on the adapter board, not the motor.

Fix

Read Present_Voltage: ~120–135 means 12 V and is healthy; ~50 means the bus is on 5 V. Power Bus 1 from the 12 V car outlet and Bus 2 through the USB-C PD cable in the parts list.

Bus drops during calibration, always at the same joint
Real cause

The cable is pulled tight when that joint reaches the end of its travel.

Fix

Leave a loop of slack cable at that joint. Don't raise the retry count to hide it: the same dropout will come back mid-grasp.

An arm falls the moment a script starts or ends
Real cause

Torque was switched off all at once. Some read-only tools release torque on purpose so you can pose the arm by hand (diagnostics/read_motors.py is one), and bus.disconnect() turns torque off by default.

Fix

Lower the arms before running anything that releases torque. In your own code, use disconnect(disable_torque=False) and step Torque_Limit down over several seconds.

A script connects, but moves the wrong arm
Real cause

Single-arm scripts use motor IDs 1–6, which is the left arm. The right arm is 7–12, so changing the port won't reach it.

Fix

Use the whole-robot teleop for two-arm work: software step 11.

Grasp lands smoothly in the wrong place
Real cause

The robot has the camera's position wrong; the arm math is fine. Swapped head tilt and pan motors, or the wrong motors read as the head, cause this.

Fix

Check that ID 1 moves the head up/down and ID 2 left/right. Then run diagnostics/debug_transform_chain.py and diagnose_fk_vs_vision.py.

UEFI Interactive Shell v2.2 — Shell> or Error: could not make network connectionJetson boots to a shell prompt
Real cause

The Jetson found nothing to boot from. The network message is not a network fault; it is the last thing it tries.

Fix

Insert a flashed microSD card, and check the firmware is 36.x for a JetPack 6 card.

When a motor bus won't respond

Check these in order, and change one thing at a time.

  1. Does the adapter show up?Run lsusb | grep 1a86 and ls /dev/ttyACM*. If nothing appears, it's a USB problem, not the motors.
  2. Does any motor answer?Run scan_port() across all baud rates. One reply means power and wiring work.
  3. One motor answers, but not the chain?Two motors share an ID. Go to Motor Configuration.
  4. The chain answers, then drops when it moves?A cable is pulled tight at a joint. Find that joint and add slack.

Camera not detected

When ls /dev/video* shows fewer cameras than you plugged in.

  1. Replug it.Unplug and replug the camera, or try another USB port.
  2. Skip the hub.Plug each camera straight into the Jetson. Keep using the same ports, since device paths change when you swap them.
  3. List the devices.Expect even-numbered entries (/dev/video0, /dev/video2), one per camera.
List video devices
$ ls /dev/video*

# To see detailed device paths:
$ v4l2-ctl --list-devices
  1. Test the camera.This one-line test should print OK.
Quick camera test
$ python -c "import cv2; cap = cv2.VideoCapture(0); ret, frame = cap.read(); print('OK' if ret else 'FAIL'); cap.release()"

Still stuck? Go back to the last "Done when" check in Software Setup that passed, and fix the first thing after it that doesn't. If that doesn't help, ask a question on GitHub (opens in a new tab).
